# 发版规范

!> **硬门禁**：没有维护者明确的"发版 / 发布 vX.Y.Z"指令，**不发布**。改完代码最多做到"本地构建 + 部署开发服 + 真机验证 + 汇报"。

## 1. 为什么要这份规范

历史上有过两天内连发多个小版本、版本号涨到 `3.9.x` 而 git tag 仍停在 `v3.1.0` 的情况：用户拿到的包无法追溯，回滚没有基准，聊天记录里也说不清"哪个包对应哪次修复"。发布是**对外承诺**，不是调试手段。

## 2. 触发与授权

| 阶段 | 允许的动作 |
|---|---|
| 日常开发 | 改代码、`npm run build`、`npm run deploy`、真机验证、把改动记进 `CHANGELOG.md` **当前版本**的段落 |
| 收到"准备发版" | 冻结改动、跑完整闸门、整理变更说明，**仍然不 tag** |
| 收到"发版 vX.Y.Z" | 按第 5 节执行一次完整发布 |

## 3. 前置清单（全部通过才可发）

| 检查 | 命令 | 通过标准 |
|---|---|---|
| 类型 | `npm run typecheck` | 无错误 |
| 配置 | `npm run check:config` | 校验模板与默认配置键集合一致 |
| 文档 | `npm run check:docs` | 链接全可达、无上游残留、无旧布局描述 |
| 版本 | `npm run check:version` | 三处版本一致且变更日志有对应段落 |
| 单测 | `npm run test:unit` | 全绿 |
| 真机 | `npm run test:live` | 输出 PASS，无 FAIL 断言 |
| 兼容 | `D:\MCserver\Master-26.51` 手工抽查 | 选区 / 复制 / 粘贴 / 预览各一次正常 |
| 变更日志 | `CHANGELOG.md` | 有 `## [x.y.z]` 段落，写清"为什么"而不是"改了啥" |

> 只改了文档或注释时，真机两项可豁免，但要在发布说明里注明"文档版本"。

## 4. 版本号策略

- 语义化：`patch` 修缺陷、`minor` 加功能、`major` 不兼容（平台基线、目录布局、配置格式）。
- 三处必须一致：`package.json` / `tooth.json` / `CHANGELOG.md`。
- `-betaN` 只在维护者明确要求预发布时使用。
- **禁止**：同一天连发多个小版本、为了"再试一次"而升版本号、同一版本重复发布。

## 5. 发布动作（按序，单次执行）

1. 确认工作区干净、CI 全绿、闸门全过；
2. 生成产物：`npm run build`（精简包）与包含依赖的全量包；
3. 打标签：`git tag -a vX.Y.Z -m "CALL x.y.z"` 并推送该标签；
4. 创建发布：`gh release create vX.Y.Z`，说明直接从 `CHANGELOG.md` 对应段落取；
5. 上传两个包（精简 + 全量），确认资产列表正确；
6. 同步文档：`docs/other/update.md` 的更新方式、README 版本矩阵（如基线变了）；
7. 回报：版本号、产物名、发布链接、验证结论。

## 6. 产物约定

| 产物 | 内容 | 用途 |
|---|---|---|
| `CALL-<版本>.zip` | 插件本体，**不含** node_modules | 常规安装；LSE 首次启动会自动装依赖 |
| `CALL-<版本>-full.zip` | 插件本体 + node_modules | 离线服务器 |

- `dist/` 是构建输出，已在忽略列表；**发布包不入库**。
- `.mcaddon` / `.mcpack` 只在用户需要手动安装资源包时由指令导出，同样不入库。

## 7. 事故与恢复

| 情况 | 处理 |
|---|---|
| 标签已存在 / 推送失败 | 先 `git tag -l` 与 `gh release list` 确认，再决定是否重试；**不重复创建同名发布** |
| 资产传错 | `gh release upload --clobber` 覆盖同名资产，**不新建版本** |
| 发布后才发现严重缺陷 | 发一个 `patch` 版本修复；**不要**悄悄替换已发布版本的包 |
| 发布说明写错 | 直接编辑该 release 的说明，不重发版本 |

## 8. 禁止项（违反即回滚）

1. 未收到指令就 bump 版本 / 打标签 / 创建发布 / 上传包；
2. 同一版本重复发布；
3. 把发布包、服务端目录、`node_modules` 提交进仓库；
4. 在文档或说明里把"未发布"写成"已发布"；
5. 用发布来"验证某次修复"，应当用开发服验证。
